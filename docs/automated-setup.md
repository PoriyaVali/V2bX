# راه‌اندازی خودکار و مدیریت گواهی

ویزارد جدید با سه ورودی کار می‌کند: آدرس پنل، کلید API و فهرست نودها به شکل
`type:id`. نوع هسته، وضعیت TLS/REALITY و دامنهٔ گواهی از پاسخ واقعی پنل خوانده
می‌شوند. برای TLS معمولی، گواهی هنگام شروع نود دریافت و در زمان لازم تمدید می‌شود.
اجرای ویزارد به‌تنهایی درخواست صدور گواهی نمی‌فرستد.

```sh
V2bX configure
```

گزینهٔ ساخت تنظیمات در `install.sh` نیز همین ویزارد را اجرا می‌کند. برای باینری‌های
قدیمی، مسیر دستی حفظ شده است؛ `V2BX_MANUAL_WIZARD=1` آن را صریحاً انتخاب می‌کند.

## اجرای بدون سؤال

کلید API را در یک فایل با دسترسی `0600` قرار دهید. مثال زیر نام فایل را به برنامه
می‌دهد تا مقدار کلید وارد آرگومان‌های فرایند یا تاریخچهٔ فرمان‌ها نشود:

```sh
V2bX configure --panel https://panel.example.com \
  --api-key-file /root/irboard-api-key \
  --nodes vless:1,hysteria2:2,mdns:3 \
  --output /etc/V2bX/config.json
```

`--api-key-env NAME` نیز پشتیبانی می‌شود. در حالت تعاملی، ورود کلید در ترمینال مخفی
است. `type:id` لازم است چون شناسه‌های پروتکل‌های مختلف در پنل می‌توانند یکسان باشند.

انتخاب خودکار، VLESS روی TCP+TLS بدون رمزگذاری افزوده و Trojan روی TCP+TLS را
برای پشتیبانی از سایت پوششی به Xray می‌سپارد؛ سایر نودهای پروکسی Sing هستند.
MDNS و TrustTunnel هستهٔ اختصاصی خود را می‌گیرند.
`--core xray` یا `--core hysteria2` انتخاب صریح هسته است و با نوع نود بررسی می‌شود.
تنظیمات REALITY، نود بدون TLS و MDNS درخواست گواهی نمی‌سازند. گواهی TrustTunnel
همچنان توسط ویزارد endpoint و تنظیمات موجود در پنل مدیریت می‌شود؛ مسیر نصب، باینری‌های
آن را نیز آماده می‌کند.

برای استفاده از سایت استاتیک خودتان، `--cover-root /var/www/node-public` را بدهید.
`--cover-title` عنوان قالب داخلی را عوض می‌کند و `--cover-tcp=false` سایت HTTPS همراه
نودهای UDP را غیرفعال می‌کند. جزئیات و پوشش هر پروتکل در
[راهنمای سایت پوششی](cover-site-security.md) آمده است.

دامنه از SNI و سپس hostname نود گرفته می‌شود؛ دامنهٔ پنل جایگزین دامنهٔ نود نمی‌شود.
Irboard اکنون hostname/SNI را برای پروتکل‌های TLS در API نود می‌فرستد. در پنل قدیمی
یا تنظیمات ناقص، ویزارد تعاملی فقط دامنهٔ گمشده را می‌پرسد؛ در اجرای بدون سؤال از
`--cert-domain node.example.com` استفاده کنید. برای صدور خودکار، hostname معتبر DNS
لازم است؛ گواهی IP و wildcard باید به‌صورت صریح تنظیم شوند.

## روش دریافت گواهی

- `--cert-mode auto` پیش‌فرض است: HTTP-01، یا DNS-01 اگر `--dns-provider` مشخص باشد.
- در HTTP-01، رکوردهای A/AAAA باید به همین سرور برسند و پورت ۸۰ از اینترنت قابل
  دسترسی باشد. برنامه سرویس وب موجود را متوقف نمی‌کند و رکورد DNS را تغییر نمی‌دهد.
- اگر وب‌سرور روی پورت ۸۰ فعال است، `--http-webroot /var/www/example` اجازه می‌دهد
  فایل challenge از همان document root و مسیر `/.well-known/acme-challenge/` سرو شود.
- برای DNS-01، از `--dns-provider cloudflare --dns-env-file /root/dns.json` استفاده
  کنید. فایل، یک شیء JSON از متغیرهای provider است، مانند
  `{"CLOUDFLARE_DNS_API_TOKEN":"YOUR_DNS_TOKEN"}`. آن را با دسترسی `0600` نگه دارید.
  توکن باید اجازهٔ ویرایش DNS دامنه را داشته باشد؛ پورت ورودی لازم نیست.
- `--cert-mode file --cert-file /path/fullchain.pem --key-file /path/private.key`
  جفت فایل موجود را پیش از ذخیره بررسی می‌کند، شامل تطابق کلید، دامنه و اعتبار زمانی.
- `--acme-email admin@example.com` اختیاری است. گواهی self-signed و غیرفعال‌کردن TLS
  برای نودی که TLS لازم دارد، در مسیر خودکار انتخاب نمی‌شوند.

گواهی‌های مدیریت‌شده زیر `certs/<domain>/` کنار فایل تنظیمات ذخیره می‌شوند و نودهای
یک دامنه از همان فایل‌ها استفاده می‌کنند. حساب ACME بین دامنه‌ها در `certs/accounts/`
مشترک است. ساخت تنظیمات جدید، تنظیمات انتخاب‌شده را بازتولید می‌کند؛ تغییرات سفارشی
فایل قبلی را از نسخهٔ پشتیبان منتقل کنید. ویزارد فایل موجود را پس از موفقیت دریافت
همهٔ نودها و بررسی JSON جایگزین می‌کند و نسخهٔ قبلی را در `.bak` با دسترسی `0600`
نگه می‌دارد. تنظیمات و نسخهٔ پشتیبان حاوی کلیدهای API/DNS هستند.

## پایداری و هزینهٔ پردازش

بررسی گواهی‌ای که هنوز به موعد تمدید نرسیده، محلی است و حساب ACME یا اتصال شبکه
نمی‌سازد. بررسی دوره‌ای هر ۶ ساعت انجام می‌شود. عملیات واقعی ACME در یک فرایند
سری می‌شوند تا نودها برای پورت ۸۰ یا فایل حساب با هم تداخل نکنند. متغیرهای DNS هر
نود پس از عملیات، حتی در صورت خطا، به مقدار قبلی برمی‌گردند.

فایل صرفاً به‌دلیل وجود داشتن پذیرفته نمی‌شود: تطابق کلید، hostname و اعتبار زمانی
بررسی می‌شوند. جفت گواهی نامعتبرِ دریافتی، فایل‌های فعال را خراب نمی‌کند. هر فایل
با rename اتمی جایگزین می‌شود و شکست نوشتن گواهی، کلید قبلی را برمی‌گرداند؛ این دو
فایل یک تراکنش مقاوم به قطع ناگهانی برق تشکیل نمی‌دهند.

هستهٔ اختصاصی Hysteria2 دیگر در هر handshake فایل‌ها را نمی‌خواند و کلید را دوباره
تجزیه نمی‌کند. گواهی تجزیه‌شده مشترک است؛ تغییر فایل‌ها حداکثر یک‌بار در ثانیه بررسی
می‌شود و جایگزین ناقص، جفت سالم قبلی را کنار نمی‌زند. این بررسی goroutine جدیدی
به‌ازای اتصال ایجاد نمی‌کند. Sing و Xray مسیر بارگذاری گواهی خود را دارند.

بنچمارک انتخاب گواهی ECDSA روی Linux amd64، Go 1.27.1 و GOMAXPROCS=4، میانهٔ سه اجرا:

| مسیر انتخاب گواهی | زمان هر انتخاب | حافظهٔ تخصیص‌یافته | تعداد تخصیص |
| --- | ---: | ---: | ---: |
| خواندن و تجزیه در هر اتصال | 36.067 µs | 7,818 B | 102 |
| مسیر گرم حافظهٔ نهان | 0.052 µs | 0 B | 0 |

این اعداد فقط هزینهٔ انتخاب گواهی را اندازه می‌گیرند؛ handshake کامل، بررسی دوره‌ای
فایل‌ها، سرعت شبکه و مصرف CPU کل سرویس را اندازه نمی‌گیرند.

آزمون‌ها شامل TLS واقعی با اعتبارسنجی گواهی، تعویض بدون restart، کلید نامطابق، فایل
ناقص، انتخاب هم‌زمان گواهی، بازگرداندن کلید پس از شکست نصب، ویزارد چند هسته، ورودی
تعاملی سه‌مرحله‌ای، حفظ تنظیمات در شکست و پوشاندن کلید API در خطاهای شبکه هستند.
آزمون‌های Race، بیلد کامل و بیلد با تگ‌های ریلیز اجرا شده‌اند. باینری ساخته‌شده نیز
تنظیمات تولید کرد، یک نود Trojan با Xray بالا آورد، handshake واقعی TLS 1.3 با بررسی
hostname و ریشهٔ گواهی انجام داد و به‌درستی متوقف شد. آزمون HTTP واقعی
Irboard برای ۱۰ پروتکل و alias قدیمی، ۳ آزمون و ۱۰۴ assertion دارد؛ مجموعهٔ گستردهٔ
پنل با استثنای پنج آزمون قدیمی GoogleAuth که با اسکیمای نصب سازگار نیستند، ۱۹۸ آزمون
و ۱۵۵۲ assertion را عبور داده است.

صدور در Let's Encrypt واقعی در این محیط اجرا نشده است؛ دامنهٔ تحت کنترل و مسیر
اعتبارسنجی عمومی برای آن لازم است. این تغییرات در ریلیز v1.9.0 ارائه می‌شوند؛
[یادداشت ارتقا](releases/v1.9.0.md) توضیح می‌دهد
کدام تغییرها با `v2bx update` فعال می‌شوند و کدام تنظیم اختیاری هستند.
